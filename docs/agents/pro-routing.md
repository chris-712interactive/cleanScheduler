# Pro routing extras (T5)

Product copy is `docs/product/pro-routing.md`. Dispatch and the single-cleaner engine stay `docs/agents/dispatch.md` and `docs/agents/routing-engine.md`.

## Decisions

- Gates are the flags already on `lib/billing/entitlements.ts`: `routeReoptimization`, `multipleStartLocations`, and `driveTimeReports`. Pro is on. Starter, Business, and the trial are off. The office sees `featureUpgradeMessage`. Field employees see neither the control nor another cleaner's home. There is no add-on SKU.
- T6 still owns billing-page treatment beyond this sentence (checkout, plan comparison, and any other surface that should mention the three tools). These screens only call `isFeatureEnabled` and `featureUpgradeMessage`.
- Re-optimize reuses `loadDispatchPlan`, `holdFixedStops`, `validateDispatchApply`, and `apply_cleaner_dispatch`. The form posts `mode=reoptimize` to `applyDispatchAction`. The plan key is the held plan. The snapshot fingerprint is still the dispatch fingerprint, so the SQL stale check is unchanged. Apply does not run by itself.
- A day counts as changed when `tenant_applied_route_days.day_fingerprint` differs from `optimizeDayFingerprint`. That hash is visits (time, status, check-in, assignees, `route_sequence`) plus approved time off that overlaps the day. `updated_at` is omitted so the apply itself does not immediately look stale. No cron.
- Finished, checked-in, and time-locked visits keep their cleaner and stop number via `holdFixedStops`. Open visits keep the optimizer's cleaner and take the remaining numbers.
- Apply still queues `queueCleanerScheduleNotice` with `scheduleVisitsFromDispatch`. No SMS. The SQL function still does not send mail.
- Start and end are `tenant_route_locations` plus `tenant_cleaner_route_bases` (`service_date` null is the default). Homes stay on `tenant_member_scheduling_profiles` and are not copied. `resolveCleanerBase` feeds `DispatchCleanerInput.start` / `end` and the single-cleaner `RouteOptimizeRequest`. The haversine plan and the Valhalla/VROOM request both use those points. An unset start is still the office, then the first stop.
- The drive-time report reads `tenant_applied_route_days` written by dispatch apply, stop-order apply, and re-optimize apply. It does not call the engine. `estimate_kind = straight-line` forces `drive_seconds` null. Engine miles and engine stop counts stay separate from the straight-line estimate. An empty range says there are no applied routes and does not print zero totals. CSV cells that start with `=`, `+`, `-`, `@`, a tab, or a carriage return are prefixed with a quote so a spreadsheet does not treat them as formulas.
- Deleting a place runs `release_route_location_bases` before the row goes away. Bases that used it become an office start and no return, so `start_kind = 'location'` is not left with a null id. The office delete control is the same Pro gate as the rest of the page.
- A start or end place must belong to the same tenant as the base. `tenant_cleaner_route_bases` references `tenant_route_locations (tenant_id, id)` for both the default row and a day override. The save action also rejects a place id that is not in this workspace. The start locations page loads the saved default and any day override so the form matches what is stored.
- `updateRouteLocationAction` edits the place row in place. The id does not change, so bases that point at it keep working. The duplicate-name check is the same unique index as insert (`23505` → "That name is already used."). An address change is `sameGeocodeAddress` from the T1 geocoder: spacing and letter case do not count as a new address. A real change calls `geocodeColumnsForAddress` and stores latitude, longitude, geocode status, and reason. The route-location table has no geocode source column, so that field is not written. If that lookup throws, the action returns "Couldn't find that address. The place was not changed." and does not update the row, so a saved map point stays. A label-only save leaves the map point alone. A new place can still be saved when its first lookup fails.
- Migration **`0134_pro_routing_extras.sql`** is already applied on shared dev and production. Do not edit it. Local-stack CI applies every file in `supabase/migrations` on the disposable database only.
- Migration **`0135_route_base_active_member.sql`** replaces `tenant_cleaner_route_bases_office`. `USING` stays `can_manage_route_office(tenant_id)`, so the office can still read and delete a base. `WITH CHECK` also requires `route_base_subject_is_active_member(tenant_id, user_id)`. That helper is security definer because authenticated has no `SELECT` on `tenant_memberships`. It returns false unless `can_manage_route_office(target_tenant_id)` is true for the caller, then it checks that the subject is an active member. A signed-in user who does not manage that tenant cannot use it to learn a membership. Anon and public cannot execute it. A user who belongs to another workspace, and an inactive member, are rejected on insert and on an update that keeps or sets that `user_id`. The same-tenant place foreign keys and `release_route_location_bases` are unchanged. This change does not apply `0135` to shared dev or production.
- RLS otherwise: owner/admin manage places and bases; a field employee can select only their own base and drive row; anon and public have no grants; authenticated cannot insert drive rows. `can_manage_route_office` is security definer so the policy does not need a membership-table grant.

## Session notes

- The QA gap was PostgREST, not the server action. An office JWT could insert `start_kind = office` for a `user_id` outside the tenant, and the row stayed on the caller's tenant. `0135` is the database close. Re-running it only replaces the helper and the one policy.
- The helper must not answer membership questions for a tenant the caller does not manage. `can_manage_route_office` is the gate inside the function, so a stranger and another tenant's employee both get false. The office `WITH CHECK` still sees true for its own active members because that caller passes the gate.
- The Start locations edit form is not in the DOM until **Edit {name}**. Its accessible names include the place name (`Street for South shed`) so they do not share the add form's Street field. `tests/local-stack/pro-routing.spec.ts` scopes those steps to `#main` and uses exact matches. After reload the list shows `street, city, state, postal` and the cleaner's saved start is still that place.
- Do not point `DATABASE_URL` at shared dev or production to prove `0135`. The local-stack job applies it on the disposable database and runs `supabase/tests/rls/pro_routing_extras.sql`.

## Gaps

- Skills, preferred cleaners, and soft zones are still not scored.
- When a fixed stop is pulled back onto its cleaner, the saved miles can still be the optimizer's miles for the list before that lock. The label stays straight-line or engine, matching the solve.
- A team visit that has not started is still pinned by dispatch. Re-optimize freezes stop numbers only for finished, checked-in, and time-locked visits.
- The Florida extract still cannot route outside Florida. A miss falls back to straight-line and is labeled as an estimate.
- Full billing UX for these flags is T6.
